RunProof: scope hackathon yang benar

  • Satu format input utama: executable JSON spec: precondition, action, expected post-state, dan recovery behavior.
  • Satu contract fixture: minimal counter di Sepolia untuk tiga skenario: baseline success, controlled gas underrun, dan simulated revert.
  • Satu agent flow: parse spec → create/validate workflow → simulate → execute → poll get_execution → assert post-state → report.
  • Bukti utama: set absolute gas limit terlalu rendah → out-of-gas → retry/recovery → success. Report harus menyebut apakah recovery dilakukan KeeperHub atau RunProof, berdasarkan hasil eksperimen Hari 1.
  • Bukti kedua: forced revert gagal pada preflight simulation dan tidak pernah dibroadcast. Revert bukan sasaran retry.
  • Provenance report: KeeperHub menyumbang execution status/logs, tx hash, gas, dan timestamp; RPC menyumbang receipt independen bila perlu; RunProof membaca pre/post-state lalu menghitung state-diff dan assertion result.
  • Stretch: publish verifier sebagai paid per-workflow MCP dan panggil lewat x402/MPP hanya setelah core execution stabil.

Yang sengaja tidak dibangun: Defender/Gelato parser, compatibility adapter, production fork simulator, multi-chain, generalized AI parser, atau security product. Tambahkan hanya bila demo inti selesai lebih awal.

Hari 1: onboarding friction ledger

Rekam layar, waktu, expected behavior, actual behavior, dan link docs. Dua gate wajib diselesaikan sebelum membangun exporter:

  • Gate recovery attribution: catat jumlah execution record sebelum dan sesudah gas underrun, lalu inspeksi setiap /logs. Tentukan apakah recovery muncul sebagai execution kedua, attempt/node log kedua dalam satu execution, atau tidak terlihat sama sekali.
  • Gate evidence: setelah baseline success, cocokkan payload aktual get_execution dengan Executions API /wait dan /logs; gunakan receipt RPC hanya untuk verifikasi independen atau field yang masih hilang.

Hipotesis friction bounty yang harus dibuktikan:

  • Ketidakkonsistenan requirement Node.js 22 vs 24.
  • Klasifikasi retry dan gas escalation tidak dijelaskan sampai level error → policy.
  • Data audit lengkap tersedia di Executions API, tetapi halaman Keeper Runs status/logs—titik masuk wajar bagi pendatang baru—hanya mengarahkan inspeksi UI/manual JSON dan tidak menautkan API tersebut. Klaim hanya jika jalur navigasi ini terulang saat onboarding.
  • Chain support global tersedia, tetapi dukungan per-plugin perlu ditemukan secara terpisah.

Bukti utama

  • KeeperHub MCP tools: workflow CRUD, validation, simulation, execution, logs, direct contract calls.
  • KeeperHub Executions API: endpoint status, wait, dan logs mendokumentasikan transaction hash, gas, timestamp, output, serta error.
  • KeeperHub Gas Management: absolute gas override dapat memicu out-of-gas; retry mungkin kembali memakai multiplier default.
  • Tenderly MCP validation: bukti demand sekaligus kompetitor langsung yang membatasi scope RunProof.
  • Tenderly Web3 Actions + Node: platform Tenderly dapat mengirim transaksi, tetapi MCP validation bukan managed recovery layer.
  • KeeperHub Defender migration guide: migrasi tetap use case sekunder, bukan premis utama.
  • DeFi Saver, Hypernative, dan Zodiac: alasan kandidat lain lebih crowded.

Keterbatasan validasi

  • Workspace belum berisi codebase, hanya hackathon.md.
  • Belum ada interview dengan builder KeeperHub; market demand belum tervalidasi sebagai willingness-to-pay. Satu pertanyaan Discord cukup selama hackathon.
  • Dokumentasi menyebut retry “may” terjadi pada out-of-gas, tetapi tidak menjelaskan apakah retry menjadi execution baru, attempt kedua dalam logs, atau hanya satu hasil akhir. Ini wajib diuji Hari 1.
  • Executions API mendokumentasikan field evidence, tetapi payload aktual get_execution, izin API, dan kebutuhan enrichment RPC tetap harus diuji pada transaksi pertama.
  • Empat friction onboarding di atas masih hipotesis sampai direproduksi; khusus audit, klaimnya adalah discoverability/linkage antardocs, bukan ketiadaan data atau API.
  • Daftar action/protocol paling otoritatif tetap harus dicek melalui list_action_schemas pada akun KeeperHub sebelum desain dikunci.
